Austin UAM Vertiport Placement — Solver Dashboard

Same 16-square Austin census board as the demand dashboard — but instead of placing vertiports by hand, a brute-force optimizer (solver_server_vertiport.py) picks where to put them, trading population access and job access against overflight noise.

How this works

1. Set a vertiport budget K and three weights — how much the optimizer should value population access, job access, and (negatively) noise.
2. Click a square's 👥 people or 💼 jobs level to cycle it 1→2→3→1 — the solver only sees these levels, so this is how you change what it thinks each zone is worth.
3. Click Run optimizer. It asks the solver server for the placement of K vertiports that maximizes the weighted objective.
4. The map highlights the chosen vertiports and draws the shortest-path corridor between every pair of them. Corridors overflying a square add to that square's noise count.
5. Read Results — who gains access, who gets jobs, who hears the noise. Adjust weights, levels, or K and re-run.

Assumptions

Zones are adjacent if they touch (including diagonally) on the 4×4 grid — that adjacency graph is what the solver routes flights through. A route between two placed vertiports takes the graph-shortest path, so it may fly over intermediate squares. Noise on a square = number of route-legs passing through it × that square's population level — so a route over a dense square costs more than the same route over a sparse one.

Population & jobs levels

The solver only understands three tiers (1 = low, 2 = medium, 3 = high) per square. Each square starts at the tier its real population and job counts rank into (tertiles across the 16 squares, same ACS/LODES data as the demand dashboard) — click a level on the map to override it and explore hypothetical zoning. Edited squares are marked edited.
